Workflow

How ideas become maintainable software.

1. Start with a Question

Most projects begin with a question instead of a feature request. Curiosity drives the process. Whether it is understanding a compression algorithm, exploring the internals of a desktop environment, or experimenting with a parser, the initial goal is to learn how something works.

Before writing code, I gather context by reading documentation, exploring source code when available, and taking notes in Obsidian. This helps me understand the problem space before committing to an implementation.

2. Build a Small Prototype

Rather than designing an entire application upfront, I begin with a minimal prototype that validates the core idea. Keeping the first iteration small makes it easy to experiment, discard assumptions, and refine the direction without being attached to early decisions.

At this stage I value clarity over optimization. Once the concept is understood, I can improve performance, architecture, and usability with confidence.

3. Iterate Through Git

Every meaningful change is tracked in Git. Commits serve as checkpoints that capture experiments, refactoring, bug fixes, and incremental improvements. Looking back through commit history often reveals how both the project and my understanding evolved over time.

I prefer frequent, focused commits over large batches of unrelated changes. This makes reviewing, debugging, and revisiting previous ideas much easier.

4. Refine the Environment

As projects grow, I refine the tools around them. Custom Neovim commands, shell scripts, Git aliases, and tmux workflows reduce repetitive work and allow me to focus on solving technical problems instead of repeating manual tasks.

Many of these improvements eventually become part of my dotfiles or are published as separate utilities.

5. Document the Journey

Documentation is part of the development process rather than something added at the end. Recording design decisions, implementation details, and lessons learned helps future contributors and also serves as a reference for my future self.

Each repository in this portfolio aims to explain not only what was built, but also why certain decisions were made.
