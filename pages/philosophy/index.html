Engineering Philosophy

The ideas that influence how I approach software.

Curiosity Comes First

I rarely start with a finished product in mind. More often, I start with a question. How does a compression algorithm reduce file size? How does a window manager decide where a window belongs? What actually happens when source code becomes executable? Those questions naturally grow into experiments, and some experiments eventually become projects worth maintaining.

For me, building software is a way of understanding systems rather than simply producing applications.

Learning by Building

Tutorials and documentation are valuable, but they become meaningful only after I apply them. I prefer implementing simplified versions of concepts before relying on mature libraries. Writing code reveals assumptions, exposes edge cases, and creates a deeper understanding than reading alone.

  • Read documentation.
  • Study implementations.
  • Build a prototype.
  • Iterate until the design makes sense.
  • Document the journey.

Understand the Layers Below

Many of my projects focus on the software beneath everyday applications: developer tools, editors, compression, desktop environments, parsers, automation, and operating system integration.

These layers are easy to overlook because they quietly support everything else. Understanding them improves the quality of every project built on top.

Developer Experience Matters

I invest time in my development environment because it directly influences how I think and work. My editor, terminal, desktop configuration, and automation scripts are not separate hobbies; they are tools that reduce friction and allow me to focus on solving problems instead of repeating manual tasks.

Small Projects Can Teach Big Ideas

A Brainfuck interpreter may never be deployed in production. A Huffman encoder might never compress my daily files. Yet each project explores techniques that appear in real systems: parsing, recursion, tree structures, binary data, performance, testing, and software architecture.

I value projects for the concepts they teach as much as the functionality they provide.

Open Source Is a Conversation

Using open source software every day naturally leads to wanting to contribute back. Reporting issues, proposing fixes, and participating in discussions are opportunities to learn from experienced maintainers while improving tools that benefit the wider community.

Continuous Improvement

"Every repository captures what I understood at a particular moment in time."

Older projects remind me how my thinking has evolved. Newer projects reflect lessons learned from earlier mistakes. I don't expect every experiment to be perfect; I expect each one to teach something useful for the next.
