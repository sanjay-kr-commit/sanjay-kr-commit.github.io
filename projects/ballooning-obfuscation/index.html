Not encryption. Not compression — the opposite of compression, on purpose. Each character gets hex-encoded, reversed, padded, and pushed through a positional keystream, so hello comes out looking like 32BD34A834D835F236E638543986. The name is literal: the data inflates.

what it is, in the author's own words

The README says it plainly

"A ASCII data obfuscation method which make data inflate."

"I'm not from cybersecurity, i made it because I thought why not."

That's the whole premise, and it's worth taking at face value: this repo is not claiming to be cryptography. It's an obfuscation scheme — something that makes text unreadable to a casual glance without pretending to survive an actual attacker. The repo has two independent takes on that idea, written a day apart, and they trade off differently.

the actual "ballooning" step

Reverse a padded hex string and the digit count grows

Every version in this repo does the same first move to each character before anything else happens to it.

Take a character, get its ASCII value, write it as 2-digit hex (h = 68). Append a throwaway digit — always 1 — making a 3-digit string (681). Reverse it (186). Parse that back as hex. The reversal is what does the inflating: reversing a 3-digit hex string and re-reading it as a number routinely produces a value with more hex digits than the original 2-digit encoding did, especially once a keystream gets added on top. Decoding just runs the same steps backward — take the resulting hex, reverse it, drop the last (throwaway) digit, and the original 2-digit hex comes back.

two scripts, one day apart

From a random salt to a password

mask.py / unmask.py

A random salt (1 to 0xFFF) is generated per message and embedded directly in the output — its own hex digit count as a length-prefix, then the salt itself. On top of that, each character position runs through a fixed quadratic (37·i² + 59·i + 101) mod 0xFFF — the "chaos step" — so the same letter at two different positions in the same message encodes differently.

Because the salt travels inside the encoded text itself, unmask.py needs no secret to reverse it — anyone with the encoded string can decode it. This version obfuscates against a glance, not against anyone willing to read unmask.py.

enc_mask.py / dec_unmask.py

The salt is dropped. Instead, each position's keystream comes from SHA256(f"{password}:{position}"), truncated to its first two bytes. Decoding needs the same password that encoding used — this version has an actual secret involved, where the first didn't.

Reusing the same password across messages reuses the exact same position-indexed keystream every time, which is the same structural weakness a two-time pad has — it's a step toward "keyed," not a step into "secure."

what this is not

Said plainly, so nobody mistakes it for security

◐ by design

This is obfuscation, not encryption. Nothing here has been reviewed against real cryptanalysis, and the README says as much up front — the value of the project was in building the round-trip, not in producing something safe to rely on.

◐ known limitation

mask.py's salt is embedded in plain sight in its own output, so it adds noise, not secrecy — anyone can run unmask.py on the encoded text with no additional information.

✓ landed

Moving from an embedded random salt to a password-derived, position-indexed keystream is a real improvement in kind, even without being a real cryptosystem — it's the difference between "no secret exists" and "a secret exists and this scheme doesn't use it very well yet."

if this gets picked back up

What an actual next version would need

  • A per-message nonce mixed into the password-derived keystream, so the same password never produces the same stream twice.
  • A real KDF (PBKDF2/Argon2) instead of a single unsalted SHA-256 call per position.
  • A clear line in the README between "obfuscation for fun" and "don't use this to protect anything real" — it's already implied, but it could be a header instead of a paragraph.
