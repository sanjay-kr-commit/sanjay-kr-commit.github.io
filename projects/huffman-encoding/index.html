PROJECT — HUFFMAN ENCODING

A compressor with no library between you and the bits.

A Huffman coder written from the frequency table up, wrapped in a small Compose Desktop app so it's actually usable instead of just a script that prints numbers. The interesting part isn't that it compresses files — it's how the tree gets written to disk without spending a full byte per path segment.

what it is

A GUI wrapper around an algorithm that didn't need one

The whole app is two buttons and two text fields: an input file, an output file, a buffer size, and a compress/decompress toggle. Click start, and it either deflate()s or inflate()s the file through a log window that streams progress line by line. There's no drag-and-drop, no native file picker — you type a path into a TextField and the app tells you whether it found the file. It's not meant to be a product. It's a way to watch the algorithm run against real files instead of a hard-coded string in a test.

Underneath the UI, the file isn't compressed as one block. It's split into fixed-size segments (bufferSize, default 1 MB), and each segment builds and stores its own Huffman tree. That's a real tradeoff: a single global tree over the whole file would usually compress better, but it means holding the whole file's frequency table in memory, or a second pass over the data. Segmenting lets the app stream — read a chunk, build a tree just for that chunk, write it, move on — at the cost of repeating tree overhead every megabyte.

why

Wanting to see the table, not just call one

java.util.zip.Deflater already does this, better, in the standard library. Using it would have taken an afternoon. Writing one from the frequency table up takes longer, and that was the point — Huffman coding is one of those algorithms that's easy to describe in a paragraph and surprisingly fiddly to actually get right once you have to serialize the tree, handle a file that isn't evenly divisible by the buffer size, and make signed bytes behave like the unsigned values they secretly aren't.

architecture

Four files, one job each

App.ktCompose window, the two screens (form + log), and the coroutine that runs deflate/inflate off the UI thread
HuffmanNode.ktthe tree itself — a data class with left/right/code/freq, plus its own serialize/deserialize logic
extensions.kteverything that turns bytes into a frequency table, a tree, a path table, and back — the actual algorithm
consts.ktone leftover line: println(128.toString(2)) — a scratchpad from working out the byte-offset trick below, never deleted

The file format written by deflate() is a flat sequence of segments: a 4-byte buffer size up front, then per segment — tree size (int), serialized tree, content size (int), and the packed bits. inflate() just reads that structure back in order. There's no index, no seeking; it's a stream in both directions.

HuffmanNode.serialize

Storing a tree without storing every path

A naive serializer writes one byte per node telling you "leaf" or "branch," then recurses. This one does that too, at first — then compresses that with a small run-length trick before it ever gets written to disk.

serializeNode walks the tree depth-first and emits 0 for a branch, or 1 followed by the leaf's byte value for a leaf. That's the naive path — one byte per tree node, which for a tree over 256 possible byte values is already a lot of 0s in a row before you hit a leaf on a long branch. deflatePath() then walks that same byte array and replaces every run of leading zeros with a single count byte: instead of 0,0,0,0,1,code you get 4,code. inflatePath() on the way back just expands each count byte into that many zeros followed by a 1. It's the same idea as run-length encoding, applied specifically to the shape of a binary tree's path bytes rather than to the file's actual content.

the -128 / +128 you'll find scattered around

Kotlin's Byte doesn't want to hold a byte value

A file byte is naturally 0–255. Kotlin's Byte is signed, -128 to 127 — the same 8 bits, different label on the range. Every place the code reads a raw byte from a file it widens it with and 0xff to get back to 0–255 for use as a frequency-table key. But when a leaf's code (that 0–255 value) gets written into the serialized tree as an actual Byte, it has to fit in -128..127 first — hence (code - 128).toByte() going out, and + 128 coming back in on deserialize. consts.kt is the one line left over from working that out by hand before trusting it to the actual code.

extensions.kt · deflate()

A file rarely divides evenly into 1 MB pieces

Every segment except (maybe) the last is exactly bufferSize bytes. The last one is shorter, and the frequency table and Huffman tree don't know that on their own — the code has to tell the decoder where the real data stops. The fix here is small and a little blunt: if a segment reads fewer bytes than the buffer size, the next unused byte is set to -1 and folded into that segment's own frequency table as a genuine symbol, so the tree learns an explicit "end of segment" leaf. It works, and it costs one symbol out of the alphabet to do it — a simpler and less efficient answer than a length-prefixed segment would have been, chosen because it reused the tree that already existed instead of adding another field to the format.

what's actually rough

The parts that would change first

◐ rough edge

There's no file picker. fileNotFound flips based on whatever string is in the text field, so a typo just quietly says "File Not Found" with no further hint. Fine for a tool you built for yourself; the first thing to fix for anyone else.

◐ tradeoff, not a bug

Per-segment trees mean a file with very uneven regions (say, a header block and a body with a totally different byte distribution) compresses better than a file that's uniform throughout but larger than the buffer — because a single global tree amortizes its overhead across the whole file, and this design pays that overhead every segment.

✓ landed

The tree-path run-length trick in deflatePath/inflatePath is a genuinely small addition that meaningfully shrinks the stored tree for skewed frequency distributions — long runs of branch nodes on the way to a rare symbol compress to a single count byte instead of one byte each.
