The decision that shaped everything after it

How do you maintain a Kotlin Multiplatform app for over a year?

Three days into the project, the architecture got picked and never really changed again: Android is naturally MVVM, so if desktop is going to share logic with it, desktop has to be MVVM-compatible too — even though desktop has no such convention on its own.

"...because android applications are Model View View Model so to retain data on refresh while keeping logic shared we have to make desktop app Model View View Model compatible, common folder holds common file shared among different platform with platform specific logic"

That single early call is why ViewModel, SharedApplicationData, and the extension system all exist as expect declarations in commonMain with separate .android.kt and .desktop.kt actuals — not because Kotlin requires it, but because the shape of an Android app was chosen as the shape of the whole app.

Six pairs of files across the codebase follow this pattern. Pick one:

desktop/util/WindowStack.kt

Desktop doesn't have Activities. So it built its own.

Android gives you onCreate / onPause / onResume / onDestroy and a back stack for free. The JVM desktop target gives you a window and nothing else — so WindowStack reimplements the Android activity model as a plain ArrayList, crossfading between entries with AnimatedVisibility. This is that stack, live.

Every extension capability ships off by default

An extension doesn't get a logger, a toast function, or the ability to open a full-screen composable just by asking. Each capability is a persisted, per-extension, per-namespace preference — the first time it's seen, it's written as false. Flip one below the way the real settings screen does, and the extension is reloaded with the new grant.

common/db/DB.kt

A version number, an H2 file, and an honest limitation

DB wraps a per-database H2 file through the Exposed framework with a single DBINFO table holding a version integer. On first run it calls onCreate. On every run after, it compares the stored version to the code's declared version — and if they don't match, it deletes every row in DBINFO and calls onVersionChange rather than running a migration path.

That's blunt by design at this stage of the project: version bumps are a signal to the app, not yet a scripted migration. Library.kt and Preferences.kt both build on this same base class.

✓ Landed

BackLambdaStack is a hand-rolled singly-linked stack instead of a Deque — on purpose, per the code's own comment, so a pushed lambda can report back whether it should be kept or removed after it runs. A small structure, built because the standard one couldn't express the return contract needed.

◐ Started, not finished

restrictedClasses declares a set of classes extensions shouldn't be able to touch (java.io.File is the only entry so far) — but nothing in the loader checks against it yet. It's a sandboxing feature that exists as a declaration and not yet as an enforcement path.

◐ Started, not finished

The real Gogoanime extension can search and list "Popular" titles, but fetchDetail, fetchPlayableContentList, and fetchPlayableMedia are still TODO("Not yet implemented"). The provider is wired into the extension system before it can actually play anything.

✓ Landed

The September 2024 rewrite touched the extension manager and loader on both platforms in the same week, moved dependency versions out of the build script into libs.versions.toml, and migrated the whole project to Kotlin 2 — a rare stretch where nothing was half-done afterward.
