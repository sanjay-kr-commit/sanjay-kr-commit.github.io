PROJECT — DEFLATE-JAR

Most of a jar is classes
nothing ever calls.

A command-line tool that opens a jar, starts from its Main-Class, and walks outward to find every class actually reachable from there — then writes a new jar with just those classes and every non-class resource. What makes it work is a shortcut: it never parses bytecode. It just checks whether one class's name shows up as text inside another class's raw bytes.

what it is

A dependency walk with no parser in it

Main.kt is barely there — it collects every .jar argument, plus any --skip fully.qualified.Name pairs, and calls deflate() on each jar. All the actual work is in deflate.kt, and it does four things in order: confirm the jar is executable (has a manifest with a real Main-Class entry that exists in the jar), read every class's raw bytes as text, follow which classes mention which other classes, and write a new jar containing only the classes that were reached plus everything that isn't a .class file at all — resources, config, whatever else the original jar carried.

why

Kotlin's compiler is generous with what it emits

Compile a small Kotlin program and the jar ends up with intrinsics, reflection metadata, and helper classes for language features the program barely touches. A real shrinker like ProGuard or R8 solves this properly by parsing the constant pool and actual bytecode instructions. This tool solves a smaller version of the same problem with something much cruder — and the second commit message says exactly what it's for: "compress generated jar remove unused class files."

deflate.kt · ZipFile.dependencyList

Why substring matching on raw class bytes actually works

A JVM class file's constant pool stores every class name it references as a plain UTF-8 string — including names it only ever uses through reflection or generated code. A single-class program is small enough that reading its raw bytes as text and checking whether another class's name appears in that text finds nearly every real reference, without ever decoding a single opcode.

dependencyList starts at the main class, reads its bytes with bufferedReader().readText() — bytes-as-text, no class-file parsing at all — and checks, for every other known class in the jar, whether that class's name (minus .class) appears anywhere in the string. Every match gets added to the allowed set and recursed into, with an inspectedList guarding against cycles. It's a heuristic, not a real reference graph, and it can over-include (a name that happens to appear as a substring of something unrelated) far more easily than it can under-include — which is exactly the safe direction to be wrong in for something whose failure mode is "the program doesn't run."

The build script uses the tool on its own output

There's no shadow/shading plugin here, so the built jar doesn't include the Kotlin runtime by default. The doLast block after the jar task adds it by hand: compile a one-line dummy Kotlin file with -include-runtime just to get a jar containing the stdlib, extract its kotlin/ package, and copy that into the freshly built jar before re-zipping it.

Then it does something a little unusual: it shells out to kotlin to run the just-built jar itself against its own output — kotlin build/libs/Deflate-Jar.jar build/libs/Deflate-Jar.jar --skip kotlin.Metadata — deflating the jar with the tool the jar itself defines, and explicitly keeping kotlin.Metadata around since Kotlin reflection depends on it existing even though nothing in a typical dependency walk would ever reach it by name.

what's actually rough

Where the heuristic can bite

◐ known gap

The --skip flag exists because the substring heuristic can miss classes reached purely through reflection with no literal name anywhere near the caller — kotlin.Metadata is the one it's actually needed for in practice, since annotation processors and the Kotlin reflection library reach it in ways the walk won't discover from Main-Class alone.

◐ known gap

String matching a class name that happens to be a common word, or a substring of an unrelated identifier, will over-include — the walk has no way to tell "this text is a real reference" from "this text just happens to contain those characters."

✓ landed

For the actual use case — one small generated jar, one entry point — the crude version is enough, and it's a fraction of the code a real constant-pool parser would need.

using it

It's just arguments

kotlin Deflate-Jar.jar MyApp.jar --skip kotlin.Metadata --skip com.example.PluginRegistry

Every .jar-suffixed argument gets processed independently; every --skip flag names a class (dots or slashes, with or without .class) that should never be dropped, regardless of whether the walk reaches it.
