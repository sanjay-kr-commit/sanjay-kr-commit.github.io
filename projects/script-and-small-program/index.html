$ ./bfInterpreter helloWorld.bf

bfInterpreter

A Brainfuck interpreter written in Kotlin. Give it a .bf file, it reads the tape, runs the eight instructions, and prints whatever falls out.

Kotlin View on GitHub

# What it does

It's a Brainfuck interpreter: eight characters — + - > < . , [ ] — operating on a tape of memory cells and a single pointer. The interpreter reads a source file, walks through it character by character, and executes each instruction against that tape. That's the entire language. No variables, no functions, no types — just a pointer, some cells, and loops.

# Why I built it

I wondered if this was possible. Brainfuck is deliberately minimal — the whole point is proving that a language this small can still compute anything a "real" language can. Writing the interpreter felt like the fastest way to actually believe that, instead of just reading about it.

# How it works

The tape is an ArrayList<Int> that starts with a single zeroed cell and grows to the right as the pointer moves past its current size. There's no fixed 30,000-cell buffer like the "classic" spec — cells get allocated lazily, on demand. A Stack<Int> tracks where each [ loop began, so ] knows where to jump back to.

Try it below — this runs the actual instruction set against helloWorld.bf from the repo, one instruction at a time, so you can watch the tape change.

tape.live
output → ▌

Note: the real interpreter doesn't bounds-check a pointer moved below cell 0 — it'll throw. This demo clamps it so the page doesn't crash on you.

# Interesting details

Loop matching isn't precomputed. When [ is hit with a zero cell, the interpreter skips forward by searching the rest of the source for the next ] using plain string search — not a real matching-bracket scan. For flat loops like the ones in helloWorld.bf that's fine. For nested loops, it would jump to the wrong ], because it has no concept of nesting depth while skipping. I noticed this reading back through the code, not while writing it.

# Challenges

Getting the jump arithmetic right took a few tries. On ], the loop start index is set to loopStart - 1, relying on the main loop's index++ at the bottom to land back exactly on the [. Off-by-one errors here don't crash loudly — they just quietly execute the wrong instruction, which is a much slower bug to notice.

# Lessons learned

A naive matching-bracket search is good enough until it isn't. If I revisit this, the fix is a jump table built once at load time — precompute every [/] pair before execution instead of re-scanning the source mid-run.

$ ./bruteForceHelloWorld

bruteForceHelloWorld

The easiest program you'll ever write, done the hardest way on purpose: every character of "Hello World" is brute-forced from a upward instead of just being printed.

Kotlin View on GitHub

# What it does

It prints "Hello World" — or whatever text you give it — one character at a time, but each character is "discovered" by counting up from a until it matches, overwriting the same terminal line as it goes. It looks like the program is cracking the string, slot-machine style, even though it already knows the answer.

# Why I built it

I wondered if this was possible — specifically, whether I could make the most boring program in programming look like it was working hard for something it already knew.

# How it works

For each character in the target string, it loops from 'a' up to that character, printing the in-progress attempt with a carriage return (\r) so it overwrites in place instead of scrolling. A Thread.sleep(10) between attempts is what actually sells the effect — without it, the "search" would resolve instantly. A -np flag turns off the trailing <- pointer.

Type something and watch the real algorithm run below.

terminal.live
 ▌

Kotlin's char ranges are ASCII-ordered, so this only "brute-forces" characters at or after a (97). Capitals, digits, and spaces sit earlier in the range — the loop body never runs for them, so they resolve instantly instead of scanning. Try "Hello World" and watch capital H and the space appear instantly while the lowercase letters scan. That's a real quirk in the code, not a bug in this demo.

# Interesting details

The instant-resolve behavior for uppercase letters and spaces wasn't planned. 'a'..i is an empty range whenever i comes before 'a' in character order, so the inner loop silently does nothing and the buffer just appends the character. The visual effect is inconsistent across a sentence purely as a side effect of ASCII ordering — which is a more interesting outcome than if I'd planned it.

# Challenges

Getting the carriage-return overwrite to look right in a real terminal took some trial and error — the buffer has to be rebuilt and reprinted in full on every single attempt, or leftover characters from a longer previous line stick around at the end.

# Lessons learned

Small, deliberately silly programs are a good place to notice language quirks — the ASCII-ordering behavior here is something I'd have never run into writing "real" code.

$ ./expressionEvaluator "2*(3+4)"

expressionEvaluator

A command-line calculator that solves expressions by rewriting the string itself — no tokenizer, no AST, no parser generator. Just string surgery, one operator at a time.

Kotlin View on GitHub

# What it does

You give it a math expression — from the command line or an interactive prompt — and it evaluates it. It supports + - * / % ^ and treats (), [], and {} as fully interchangeable brackets, so 2*[3+{4}] is valid. It also inserts implicit multiplication: 2(3) is read as 2*(3).

# Why I built it

I wanted to see how far I could get evaluating math without building a "real" parser — no tokens, no tree, just treating the expression as a string and repeatedly rewriting it in place until one number is left.

# How it works

Every operation follows the same shape: find an operator character in the string, walk backward and forward from it to pull out the two numeric operands (digit by digit), compute the result, and splice it back into the string in place of "a+b". That function gets called on repeat, in BODMAS order — ^, then /, then *, then +, then -, then % — until nothing matches. Brackets are resolved innermost-first by finding the last open bracket and its matching close, evaluating what's between them, and substituting the result back in.

evaluator.live

The trace shows each rewrite step the real algorithm performs — this is the same string-surgery approach as the Kotlin source, reimplemented in JS for the browser.

# Interesting details

Exponents don't call a power function. a^b gets expanded into a literal repeated-multiplication string — a*a*a..., b times — and then the normal multiplication pass evaluates that. It's a strange way to do it, but it kept the entire evaluator down to one small family of operations instead of needing a special case.

# Challenges

Telling subtraction apart from a negative sign was the fiddliest part. 3+-4 and -3+4 both contain a -, but only one of them is a binary operator at that index. The fix ended up being a plain position check — subtraction only fires if the - isn't at the very start of the string — which is a blunt rule, but it holds for everything the validator lets through.

# Lessons learned

String rewriting is a genuinely fun constraint to work under, but it re-scans the whole expression after every single operation, so it doesn't scale well to long expressions. A real tokenizer feeding an AST would be the sensible next version — this one was about seeing how far the string-only approach could go.

$ ./injectBashStartup Main.kt

injectBashStartup

A bash script that compiles a Kotlin or Java program, then staples a small bootstrap script onto the front of the compiled output — so the result runs directly, like a binary.

Bash View on GitHub

# What it does

It does what a #! shebang does for a Python or bash script, but for compiled JVM output. Normally you'd run a compiled program with java -jar thing.jar or kotlin Thing.kt. This wraps the compiled file so you can just run ./thing instead — the interpreter name is baked into the file itself.

The project's own README is upfront about this: "Don't confuse it with a compiler." It still needs a JVM (and kotlinc or javac) present on the machine — this is a convenience wrapper, not a standalone executable format.

# Why I built it

Typing kotlin Program.kt or java -jar program.jar every time got tedious, and I wanted to know if I could make a compiled JVM file behave like a native binary using nothing but bash and some careful byte counting.

# How it works

The script checks the file extension you give it (.kt, .java, or an existing .jar), compiles it with kotlinc or javac into a scratch directory — preferring /dev/shm so the temp files live in memory — and then builds a bash header as a heredoc string. That header is concatenated in front of the compiled bytecode with cat, and the result is marked executable.

anatomy of the wrapped file
bash header #!/bin/bash — locates itself, extracts the payload, runs it
compiled bytecode the original .class / .jar contents, byte for byte

    # Interesting details

    When the wrapped file runs, it has to cut itself back apart — separating its own bash header from the bytecode glued onto the end of it — using sed and head with a hardcoded line count. If the java process modifies the file during execution (which happens in some jar self-write scenarios), the script re-appends the header afterward by comparing a checksum of the payload before and after the run.

    # Challenges

    The whole thing is held together by exact line-count offsets — sed -e '1,47d', head -48 — that have to match the header's real length precisely. Change one line in the injected header and the split breaks, silently corrupting the binary portion. It works, but it's brittle by construction, and the README's warning not to mistake it for a compiler is doing real work.

    # Lessons learned

    Hardcoded byte/line offsets are a fast way to get a shebang-style trick working, but a length-prefix or an explicit boundary marker in the file would be a lot less fragile than counting lines by hand.
