PROJECT — DOTFILES

Not a config folder.
A shell that configures itself.

Ten modules, a loader that reads their own comments to decide what depends on what, and a boot script that will re-clone the whole thing from GitHub if it ever wakes up on a machine that's never seen it before. This is a tour of how it actually works.

zsh — ~/dotfiles
$ cat ~/.zshrc

One line in .zshrc. Everything else earns its place.

Why is your shell built this way?

Because a `.zshrc` that's five hundred lines of copy-pasted Stack Overflow answers is unmaintainable, and a `.zshrc` that's one line pointing at a real program is not. The only thing that gets sourced directly is configureshell — everything downstream of it is code, not config.

The first thing configureshell does is refuse to run anywhere it shouldn't. It checks the active process against zsh and the parent shell against a small known-list, and if either check fails, it prints why and bails — no silent partial setup on a bash box.

Then it builds something most dotfiles repos never need: its own path resolver. Every downstream script calls processRelativePath instead of cd, which pushes onto a hand-maintained stack (_path_stack), resolves .. segments with a character-by-character loop, calls the target script, and pops the stack back on return. No script ever changes the shell's actual working directory just to find its neighbours.

~/dotfiles/runtime

Two boots: the first one, and every one after

Everything in runtime/ is the engine. Adding a feature never means touching this folder — it means dropping a new file in module/.

--init
First shell ever on this machine. initscript routes to setup, which checks whether .zshrc already sources the dotfiles. If not, it works out the repo's own git remote origin and writes a small conditional block back into .zshrc: if this directory exists, source it — otherwise clone it from origin, then source it.
↓ every later shell
initialize
Calls flagFunctions (exposes :flag), then moduleFunction (exposes :module), then hands off to moduleloader — always in that order, so the toggle commands exist before any module that might want to call them.

The payoff of the self-cloning stanza: hand a fresh Arch install the git URL once, and the next shell you open finishes the rest by itself.

~/dotfiles/module

Modules describe themselves. The loader just reads.

How does a plain shell script declare a dependency?

In a comment. moduleloader greps every enabled module for three markers before it sources anything:

p->
Load priority. Lower runs first. tmux_terminal is -100 because a fresh terminal should attach to tmux before anything else happens. persistentAlias is 1002 — it wants every other module's aliases already defined before it starts intercepting alias calls.
d->
Dependencies. resolveDependency recurses through these before sourcing the module itself, and skips anything already loaded so two modules requesting the same dependency don't double-source it.
f->
Flags the module wants registered dynamically — persistentAlias declares USE_RAM_FOR_TEMP_ALIAS_FILE this way, so :flag can toggle it without runtime/LIST_OF_FLAGS needing to know about every module in advance.

The real load order comes from an awk script that anchors named priorities in place and slots the unnamed modules into the gaps between them. Here's the current result:

~/dotfiles/config/public/persistentAlias/STORED_ALIASES

An alias that survives a restart, on purpose

This module overrides the alias builtin. Calling alias --save name=cmd doesn't just define it for the session — it rewrites STORED_ALIASES line-by-line, replacing an existing entry in place if one exists rather than appending a duplicate. unalias --delete does the same surgery in reverse.

~/dotfiles/module/gitPass

One git command, several identities

How do you avoid setting user.email by hand in every clone?

01
git is redefined as a function. It reads the current repo's remote get-url origin and pulls the host-relative username out of the URL.
02
That username is looked up in a private, gitignored userconfigs file. Found → the matching email is set as user.name / user.email for this call only. Not found → falls back to whatever ~/.gitconfig already says.
03
The real command runs with GIT_ASKPASS pointed back at the same script, which detects it's being invoked as an askpass and answers the username / password prompt itself from that same private file — so a push never stops to ask.

No secret ever sits in the visible dotfiles — config/private/ is gitignored and populated per-machine with :addGitUser.

~/dotfiles/module/sudo_systemd_ask_pass

A clearer prompt for a two-line wrapper

Same self-referential-askpass trick as gitPass, applied to sudo and sudoedit: both are redefined to route through SUDO_ASKPASS, which calls back into the script to invoke systemd-ask-password with a message that actually says "sudo password" instead of the generic systemd string — and the wrapper captures and returns the real exit code, so a failed sudo still fails the script that called it.
