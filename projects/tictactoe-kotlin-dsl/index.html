what it is, in the author's own words

The README doesn't oversell it

"A fancy way of writing tic tac toe with kotlin dsl and extension function"

"it not optimised for playing but more of an art project i just wanted to make a structured code like jetpack compose"

That's the whole brief. The board, the win check, the bot — none of it is trying to be clever as an algorithm. What's actually being explored is the shape of the code: can a two-player grid game read like a builder DSL, the way Compose turns UI trees into nested lambda calls? The answer here is yes, at the cost of a fair amount of ceremony for something this small — and that tradeoff is the point.

architecture

Seven files for one game of tic-tac-toe

Board.ktthe 3×3 array, plus the infix mark functions that are the whole point of the DSL
Coordinates.kta tiny scope type — row/column as ScopedSpot (First/Second/Third), so a coordinate reads as a word instead of a 0-indexed int
GameCharacterScope.ktwraps X/O as properties in scope, and — in its companion object — hosts extension functions on Board: gameStatus(), playing, result
Bot.kta static, rule-based botSpot — check every line for a win, then for a block, else pick at random
InvalidSpotException.kt / SpotAlreadyOccupiedException.ktthe DSL fails loud instead of returning a boolean when a move doesn't make sense
Main.ktthe whole game, expressed as nested builder lambdas
Main.kt

What the DSL actually buys you

fun main() : Unit = board {
    gameCharacter {
        player = X
        bot = O
        priority = X

        playing { turn ->
            if (turn == bot) {
                turn mark botSpot
            } else turn mark {
                row = readln().toInt().scopedSpot
                column = readln().toInt().scopedSpot
            }
        }

        println(result)
    }
}

board { } and gameCharacter { } are builder functions — each just invokes its lambda with a fresh receiver, the same pattern Compose uses for every composable. Inside, X and O aren't global constants; they only exist as properties of GameCharacterScope, so they're only in scope where a game character actually makes sense. And turn mark botSpot versus turn mark { row = ...; column = ... } are the same infix function with two different call shapes — one takes a raw index, the other takes a lambda that fills in a nested Coordinates scope one field at a time.

GameCharacterScope.kt · companion object

Extension functions living on the "wrong" class

gameStatus(), playing, and result are all extension functions on Board — but they're declared inside GameCharacterScope's companion object, not Board's.

That placement is deliberate, not an accident of where the file happened to live: those functions need GameCharacter.X/GameCharacter.O in scope to read naturally, and putting them behind GameCharacterScope.Companion means they're only available once you've imported the DSL surface — import GameCharacterScope.Companion.playing — rather than being globally attached to every Board everywhere. It's using Kotlin's extension-function import scoping as a crude form of access control: the capability exists, but only where the DSL has been explicitly opted into.

the recursive version that didn't make it

A whole abandoned algorithm, left in as a comment

The static gameStatus() that shipped is a flat when block checking all eight winning lines by hand. Directly above it in the same file, commented out, is a different approach entirely — a recursive version that tries to walk the board diagonally from each cell, checking three directions at once and propagating Undetermined/Draw/a winning character back up through the recursion.

It's left in rather than deleted — a record of trying the more "elegant" recursive idea first, running into how awkward it gets to reason about three simultaneous recursive branches and a nullable dual-purpose parameter, and shipping the flat, boring version that's actually easy to verify by reading it once.

the last commit of the day

One line that tells you exactly how the afternoon went

"add a doLast Task to jar Task to add kotlin runtime files to jar after the jar has been compiled i thought why use library for such a simple thing how hard it would be it was hard"

Without a shading plugin, a plain Kotlin jar doesn't carry the Kotlin stdlib with it — so a build script step has to compile a throwaway file with -include-runtime, extract the runtime classes from that, and copy them into the real jar after it's built. It's a small, well-defined problem that looks like it should take ten minutes, right up until you're the one writing it by hand instead of enabling a plugin. The same exact problem shows up independently in this portfolio's Deflate-Jar project's build script too — not copied between them, just the same rough edge in the Kotlin/Gradle toolchain, found twice.
